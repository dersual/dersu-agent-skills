# Coding-Agent Permission Design: Allowlist vs. Denylist vs. OS Sandboxing

Research on permission architectures, bypass risks, and exact evaluation mechanics across **Anthropic Claude Code**, **OpenCode**, **OpenAI Codex**, and **Google Antigravity** (`agy`).

---

## 1. Allowlist vs. Denylist vs. OS Sandboxing

### 1.1 First-Party Recommendations

All four platforms recommend **OS-level sandboxing** combined with **fail-closed defaults** (`ask` for unconfigured actions) and **narrow allowlists** for routine commands. None recommend `shell * -> allow` with a denylist on an unsandboxed host.

| Harness | Recommended Default Posture | OS Sandbox Mechanism | Primary Source |
| :--- | :--- | :--- | :--- |
| **Claude Code** | Fail-closed (`default` / `auto` mode with classifier) + narrow allowlists + Bash Sandbox | macOS Seatbelt; Linux/WSL2 `bubblewrap` + `socat` (no native Windows sandbox) | [Claude Code Permissions](https://code.claude.com/docs/en/permissions.md), [Sandboxing](https://code.claude.com/docs/en/sandboxing.md), [Security](https://code.claude.com/docs/en/security.md) |
| **OpenCode** | Broad `ask` (`shell * -> ask`) + narrow `allow` rules (`git status *`, `git diff *`) + `policies` `deny` | None built in (`shell` runs with full host user authority) | [OpenCode Permissions](https://opencode.ai/docs/permissions/), [OpenCode Policies](https://opencode.ai/docs/policies/) |
| **OpenAI Codex** | `workspace-write` sandbox (network off) + `on-request` approvals (`Auto` preset) + `.rules` for escalations | macOS Seatbelt (`sandbox-exec`); Linux/WSL2 `bwrap` + `seccomp`; Windows MXC/Windows Sandbox | [Codex Approvals & Security](https://learn.chatgpt.com/docs/agent-approvals-security.md), [Codex Sandboxing](https://learn.chatgpt.com/docs/sandboxing.md), [Codex Rules](https://learn.chatgpt.com/docs/agent-configuration/rules.md) |
| **Antigravity (`agy`)** | `Default` (App) / `auto` (CLI `v1.5.7+`) with Terminal Sandbox on + explicit `allow`/`ask`/`deny` | macOS `sandbox-exec`; Linux namespaces; Windows 11 24H2+ (Aug 2026+) AppContainer | [Antigravity Permissions](https://antigravity.google/docs/permissions.md), [Antigravity Sandbox](https://antigravity.google/docs/sandbox.md), [CLI Modes](https://antigravity.google/docs/cli/modes.md) |

Key primary-source statements:

- **OpenCode**: Explicitly warns against `shell * -> allow` + `deny`. *"shell runs with the host user’s filesystem, process, and network authority. Directory inference from command text is best effort, so prefer a narrow shell allowlist instead of patterns intended to recognize every dangerous command."* ([OpenCode Permissions](https://opencode.ai/docs/permissions/))
- **Claude Code**: *"A Bash rule matches the command text Claude writes... It doesn't match the same program invoked in a different form, so a deny or ask rule covers the invocation Claude usually produces and isn't a security boundary around the program... For filesystem and network enforcement that doesn't depend on the command text, use sandboxing."* ([Claude Code Permissions](https://code.claude.com/docs/en/permissions.md))
- **Claude Code (`auto` mode)**: Drops broad allow rules such as `Bash(*)` automatically when `auto` mode is active. ([Claude Code Auto Mode Config](https://code.claude.com/docs/en/auto-mode-config.md))
- **OpenAI Codex**: Marks `--dangerously-bypass-approvals-and-sandbox` (`--yolo`) as *"EXTREMELY DANGEROUS. Intended solely for running in environments that are externally sandboxed"*. (`codex --help`; [Codex Approvals & Security](https://learn.chatgpt.com/docs/agent-approvals-security.md))

### 1.2 Documented Security and Bypass Risks of `shell * -> allow` + `deny` (Without OS Sandbox)

Command-string `deny` and `ask` rules inspect the text generated by the model, not the OS syscall or process tree. Without an OS sandbox, primary docs document five bypass classes:

1. **Alternate binary paths**: A rule such as `Bash(curl *)` or `Bash(rm *)` blocks `curl` or `rm`, but does not match `/usr/bin/curl` or `/bin/rm`. ([Claude Code Permissions](https://code.claude.com/docs/en/permissions.md))
2. **Subshells and interpreter wrappers**: Invocations such as `sh -c 'curl ...'`, `bash -c 'rm -rf build/'`, `python -c '...'`, or `node -e '...'` hide the inner command behind an allowed outer binary. ([Claude Code Permissions](https://code.claude.com/docs/en/permissions.md))
3. **Flag reordering and pre-subcommand options**: `Bash(git push *)` blocks `git push origin main`, but does not match `git -C . push origin main` or `git -c push.default=current push origin main`. ([Claude Code Permissions](https://code.claude.com/docs/en/permissions.md))
4. **Variable expansion and indirection**: Patterns such as `URL=http://github.com && curl $URL` evade argument-level text matching. ([Claude Code Permissions](https://code.claude.com/docs/en/permissions.md))
5. **Unstripped runners and dynamic evaluation**:
   - **Claude Code**: Environment runners (`direnv exec`, `devbox run`, `mise exec`, `npx`, `docker exec`) and exec wrappers (`watch`, `setsid`, `ionice`, `flock`, `find -exec`/`-delete`) are not stripped as transparent wrappers. ([Claude Code Permissions](https://code.claude.com/docs/en/permissions.md))
   - **OpenCode**: Dynamic evaluation (`eval`) or malformed syntax cannot be split by the shell scanner. If any shell `deny` rule exists, unparseable commands fail with a scanner error; otherwise they fall back to whole-command approval. ([OpenCode Permissions](https://opencode.ai/docs/permissions/))
   - **OpenAI Codex**: Scripts using redirections (`>`, `<`), substitutions (`$(...)`), env assignments (`FOO=bar`), globs (`*`, `?`), or control flow (`if`, `for`) are not split by tree-sitter and are evaluated only as `["bash", "-lc", "<full script>"]`. ([Codex Rules](https://learn.chatgpt.com/docs/agent-configuration/rules.md))
   - **Antigravity**: Command/process substitution (`$(...)`, backticks, `<(...)`), `$((...))`, brace expansion (`{a,b}`), non-literal command names, network/FD redirections, and subcommand flags (`git -c core.pager=<cmd>`, `tar --to-command`) disable prefix matching and fall back to **Ask** unless matched character-for-character or by `regex:`. ([Antigravity Permissions](https://antigravity.google/docs/permissions.md))

### 1.4 Recommendations for Language Runtimes (`python`, `node`, `npm`, `dotnet`)

Language runtimes execute arbitrary code (`python -c`, `node -e`, `npx`, `dotnet run`), so command-name allowlists alone do not constrain what they do.

- **Scope script runners to subcommands**:
  - **Claude Code** recommends `Bash(npm run *)` rather than `Bash(npm *)` (which would permit `npm install` or `npm exec`), and warns that `npx` executes arbitrary packages. ([Claude Code Permissions](https://code.claude.com/docs/en/permissions.md))
  - **Antigravity** recommends regex-scoped subcommands such as `command(regex:npm run (build|lint|test))`. ([Antigravity Permissions](https://antigravity.google/docs/permissions.md))
- **Contain runtimes with an OS sandbox, not regexes**:
  - **Claude Code**, **Codex**, and **Antigravity** run `python`, `node`, `npm`, and build tools inside the OS sandbox so child processes inherit workspace-only write limits and network domain restrictions (e.g., `registry.npmjs.org` or `*.pythonhosted.org` in Claude Code's sandbox proxy). ([Claude Code Sandboxing](https://code.claude.com/docs/en/sandboxing.md), [Codex Sandboxing](https://learn.chatgpt.com/docs/sandboxing.md), [Antigravity Sandbox](https://antigravity.google/docs/sandbox.md))
  - **OpenCode** has no built-in OS sandbox, so allowing `python *`, `node *`, or `dotnet *` grants full host user authority. ([OpenCode Permissions](https://opencode.ai/docs/permissions/))

## 2. Exact Mechanics in OpenCode and Antigravity

### 2.1 OpenCode (`opencode.ai/docs` and `opencode --help`)

1. **Does `shell * -> allow` followed by `ask` work?**
   - **Yes.** In V2 (`permissions` array in `opencode.jsonc`), OpenCode evaluates rules in order using **last-match-wins**. Placing `{ "action": "shell", "resource": "*", "effect": "allow" }` first and narrower `ask` or `deny` rules after it causes the later rule to win. ([OpenCode Permissions](https://opencode.ai/docs/permissions/))
   - For compound commands that touch multiple resources, OpenCode applies: **any `deny` denies; otherwise any `ask` asks; otherwise allowed**. ([OpenCode Permissions](https://opencode.ai/docs/permissions/))

2. **How do `policies` (`tool.use`) work?**
   - `policies` are binary (`allow` or `deny`, never `ask`) and are evaluated **after** agent `permissions` rules and saved `"Allow always"` approvals. ([OpenCode Policies](https://opencode.ai/docs/policies/))
   - Precedence is **authority-reversed**: managed/system/Console/global policies override project/user config. A `tool.use` `deny` overrides both `allow` and `ask` with `Blocked by configuration policy`. ([OpenCode Policies](https://opencode.ai/docs/policies/))

3. **How does `--auto` (Orca `Full access`) interact with `ask` vs. `policies`?**
   - `opencode --help` and `opencode run --help` define `--auto` as: **`Auto-approve permissions that are not explicitly denied`**.
   - Therefore, `--auto` **auto-approves `ask` rules** without prompting, while **`deny` rules in `permissions` and `tool.use` `deny` statements in `policies` remain strictly enforced**. (`opencode --help`; [OpenCode Permissions](https://opencode.ai/docs/permissions/))

### 2.2 Antigravity (`agy --help`, `settings.json`, `antigravity.google/docs`)

1. **Does `command(*)` work in `allow`?**
   - **Yes.** Under *CLI global wildcard syntax*, passing `*` matches all targets within an action namespace (`command(*)`, `read_file(*)`, `mcp(*)`). ([Antigravity Permissions](https://antigravity.google/docs/permissions.md))
   - **Windows caveat**: On Windows shells (PowerShell / `cmd.exe`), commands that cannot be cleanly split into words require an exact match unless you use `regex:` (e.g., `command(regex:git .*)`). ([Antigravity Permissions](https://antigravity.google/docs/permissions.md))

2. **What is the exact evaluation order?**
   - **Strict tier precedence: `Deny > Ask > Allow`**, regardless of rule order or specificity. ([Antigravity Permissions](https://antigravity.google/docs/permissions.md), [Antigravity Settings](https://antigravity.google/docs/settings.md))
   - Example: If `command(*)` is in `allow`, any matching rule in `ask` (e.g., `command(git push *)`) or `deny` (e.g., `command(rm -rf /)`) still takes precedence over `allow`. ([Antigravity Permissions](https://antigravity.google/docs/permissions.md))

3. **How does `auto` mode vs. `Full access` (`--dangerously-skip-permissions` / `always-proceed`) behave?**
   - **`auto` mode** (`--mode=auto` or `"agentMode": "auto"`, default in `agy` `v1.5.7+` when the sandbox is available):
     - Automatically enables the OS Terminal Sandbox and approves workspace file edits.
     - Commands inside the sandbox run without prompting; commands needing to run outside the sandbox are evaluated automatically (safe/reversible run, risky/irreversible prompt).
     - Explicit `deny` and `ask` rules in `settings.json` still take precedence (`Deny > Ask > Allow`). ([Antigravity Permissions](https://antigravity.google/docs/permissions.md), [CLI Modes](https://antigravity.google/docs/cli/modes.md))
   - **`always-proceed` (`toolPermission` in `settings.json`) / `--dangerously-skip-permissions` (`agy --help`)**:
     - `agy --help` documents `--dangerously-skip-permissions` as: **`Auto-approve all tool permission requests without prompting`**.
     - `agy_permissions.md` and `agy_cli_modes.md` note that `always-proceed` (`--dangerously-skip-permissions`) overrides `auto` mode, while explicit `deny` rules block actions in every mode. `agy_settings.md` specifies `toolPermission: "always-proceed"` runs commands, web requests, and MCP tools without prompting *"except actions that match an ask or deny rule"*. ([Antigravity Settings](https://antigravity.google/docs/settings.md), [Antigravity Permissions](https://antigravity.google/docs/permissions.md), `agy --help`)
